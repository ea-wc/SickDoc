# Data Model

PostgreSQL via Prisma. All timestamps are `timestamptz` stored in UTC. All ids are
`uuid` generated by the database. Monetary and clinical content is fictional.

## 1. Entity relationships

```
User 1─1 PatientProfile        User 1─1 DoctorProfile
                                      │
                                      ├─* DoctorSpecialization *─1 Specialization
                                      ├─* AvailabilityRule
                                      └─* AvailabilityException

PatientProfile 1─* Appointment *─1 DoctorProfile
                        │
                        ├─1 ConsultationSession
                        ├─0..1 ConsultationNote
                        └─0..* Prescription 1─* PrescriptionItem

Symptom *─* Specialization  (via SymptomSpecialty, weighted)

User 1─* Notification        User 1─* RefreshToken
User(admin) 1─* AuditLog
```

## 2. Enums

```prisma
enum Role              { PATIENT DOCTOR ADMIN }

enum SessionStatus     { SCHEDULED JOINED IN_PROGRESS COMPLETED CANCELLED NO_SHOW }

enum NotificationType  { APPOINTMENT_BOOKED APPOINTMENT_RESCHEDULED APPOINTMENT_CANCELLED
                         APPOINTMENT_REMINDER SCHEDULE_CHANGED CONSULTATION_READY
                         NOTE_AVAILABLE PRESCRIPTION_ISSUED DOCTOR_PROFILE_REVIEWED
                         ACCOUNT_STATUS_CHANGED }

                         DOCTOR_APPROVED DOCTOR_REJECTED DOCTOR_PROFILE_UPDATED
                         APPOINTMENT_CANCELLED APPOINTMENT_RESOLVED }
```

`Specialization`: `id`, `slug` (unique, e.g. `cardiology`), `name`, `description?`,

`DoctorSpecialization`: `doctorProfileId`, `specializationId`, `isPrimary` (bool).
Composite PK `(doctorProfileId, specializationId)`.

## 5. Scheduling

### AvailabilityRule

Recurring weekly availability.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `doctorProfileId` | uuid | FK, cascade |
| `weekday` | int | 0 = Sunday … 6 = Saturday |
| `startMinute` / `endMinute` | int | minutes from midnight in the doctor's timezone; `start < end` |
| `slotMinutes` | int | default 30 |
| `effectiveFrom` / `effectiveTo` | date? | optional validity window |
| `isActive` | bool | default true |

Index: `(doctorProfileId, weekday)`.

### AvailabilityException

A blocked window that subtracts from the rules — leave, a conference, a blocked morning.

`id`, `doctorProfileId`, `startsAt`, `endsAt`, `reason?`. Index `(doctorProfileId, startsAt)`.

Concrete bookable slots are **derived at read time** from rules minus exceptions minus
active appointments minus slots that have already started. No slot table exists; see
[ARCHITECTURE.md](ARCHITECTURE.md) §6.1.

### Appointment

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `patientProfileId` | uuid | FK |
| `doctorProfileId` | uuid | FK |
| `startsAt` / `endsAt` | timestamptz | UTC; `endsAt > startsAt` |
| `status` | AppointmentStatus | default `CONFIRMED` |
| `reason` | text | patient's stated concern |
| `symptomIds` | uuid[] | symptoms selected during matching, for context |
| `rescheduledFromId` | uuid? | self-FK to the superseded appointment |
| `cancelledAt` | timestamptz? | |
| `cancelledBy` | CancelledBy? | |
| `cancellationReason` | text? | |
| `createdAt` / `updatedAt` | timestamptz | |

Indexes: `(doctorProfileId, startsAt)`, `(patientProfileId, startsAt)`, `status`.
Partial unique index on `(doctorProfileId, startsAt)` where
`status IN ('PENDING','CONFIRMED','RESCHEDULED')` — the database-level guard against a
double booking that races past the transaction.

## 6. Consultation and records

### ConsultationSession

One per appointment, created at booking.

| Field | Type | Notes |
|---|---|---|
| `id` | uuid | PK |
| `appointmentId` | uuid | FK, unique, cascade |
| `status` | SessionStatus | default `SCHEDULED` |
| `patientJoinedAt` / `doctorJoinedAt` | timestamptz? | |
| `startedAt` / `endedAt` | timestamptz? | |
| `durationSeconds` | int? | computed on completion |

### ConsultationNote

At most one per appointment; written by the appointment's doctor.

`id`, `appointmentId` (unique FK), `authorUserId`, `subjective?`, `objective?`,
`assessment`, `plan`, `summary`, `followUpAt?`, `createdAt`, `updatedAt`.

Visible to the patient once the session is `COMPLETED`.

### Prescription / PrescriptionItem

`Prescription`: `id`, `appointmentId` (FK), `issuedByUserId`, `patientProfileId`,
`issuedAt`, `notes?`, `validUntil?`.

`PrescriptionItem`: `id`, `prescriptionId` (FK, cascade), `drugName`, `dosage`,
`frequency`, `durationDays?`, `instructions?`.

Index: `(patientProfileId, issuedAt desc)`.

## 7. Matching

### Symptom

`id`, `slug` (unique), `label`, `synonyms` (text[]), `bodySystem?`.

### SymptomSpecialty

Weighted many-to-many that makes matching deterministic.

| Field | Type | Notes |
|---|---|---|
| `symptomId` | uuid | FK, part of composite PK |
| `specializationId` | uuid | FK, part of composite PK |
| `weight` | int | 1–10; higher means a stronger indication |

Free-text symptom input is normalized and matched against `slug` and `synonyms`
locally. No model, no network call.

## 9. Integrity rules enforced in the database

- Unique: `User.email`, `DoctorProfile.licenseNumber`, `Specialization.slug`,
  `Symptom.slug`, `ConsultationSession.appointmentId`, `ConsultationNote.appointmentId`.
- Partial unique on active appointments per doctor and start time.
- Check constraints: `endsAt > startsAt` on `Appointment` and `AvailabilityException`;
  `startMinute < endMinute` and `slotMinutes > 0` on `AvailabilityRule`;
  `weight BETWEEN 1 AND 10` on `SymptomSpecialty`.
- Cascade delete from `User` to its profile, refresh tokens, and notifications.
  Clinical records are **not** cascade-deleted with a profile; deactivation sets
  `UserStatus.DEACTIVATED` and retains history.

## 10. Seed data

`prisma/seed.ts` provisions a demonstrable system: 1 admin, ~8 approved doctors
across 6 specializations plus 1 pending doctor for the review flow, ~5 patients with
profiles, ~30 symptoms with weighted specialty mappings, weekly availability for each
doctor, and a spread of past, upcoming, and completed appointments — the completed
ones carrying notes and prescriptions so the records screen is not empty on first run.
Seed credentials are documented in the README and are placeholders, not secrets.
